# 10 前端接入与工程规范

> 面向：前端开发 / 联调同学。核心结论是「平台的接入项都是注册制，不能自建」。

## 1 接入分三层

| 层 | 承担方 | 作用 |
|---|---|---|
| **门户注册层** | 五矿个人门户「能力中心 > 应用管理」 | 登记应用编号、名称、负责人、服务地址，建立应用与门户的对应关系 |
| **宿主（主应用）层** | 门户前端宿主平台，用 `wujie` 的 `startApp` 加载子应用 | 登记子应用 `name`、`url`、`plugins`（共享依赖替换） |
| **部署与网关层** | 子应用 nginx | `/micro/<appCode>/` 提供静态资源、`/biz-gateway` 代理业务网关、`/fe-shared-deps` 提供共享依赖 |

门户侧入口统一是「能力中心 > 应用管理」（左侧「基础平台」菜单下），这是所有配置说明书的统一起点。

## 2 必须准备的注册项

**1）应用注册（门户）**
- 必填：**应用编号、应用名称、负责人、服务地址**。
- 编号示例：`app-minmetals-fm-fis-base`、`app-minmetals-fm-fis-apa`；配置说明书示例里「应用名称」与「应用编号」填同一个值。
- 命名规律参考 `app-<组织>-fm-fis-<模块>`，**先与门户管理员确认命名规则再固定使用** —— 后续路由、部署目录、宿主 `name` 都依赖它。

**2）宿主侧微应用注册（wujie）**
- 文件位置示例：`src/micro/index.js`。
- 关键项：`name`（子应用唯一标识）、`url`（子应用完整部署地址，如 `https://financial-test.minmetals.com.cn/micro/minmetals-fm-fim-fus-lc/`）、`plugins`（替换子应用 importmap，复用宿主共享依赖）。
- 若接 QianKun，对应的是 `name`、`entry`、`container`、`activeRule`；但检索到的材料只把 QianKun 登记为「微前端工具库」，**没有 QianKun 主应用的具体配置代码**。

**3）路由与 base**
- 部署路径决定 base：nginx 中 `location /micro/fin-ast` 用 `alias /home/app` 指向产物，并 `try_files $uri $uri/ /micro/fin-ast/index.html` 做 SPA 回退。
- 因此子应用构建 `publicPath`、路由 base（history 模式）**都必须是 `/micro/<appCode>/`**，与部署目录严格一致。

**4）API 与网关**
- 统一前缀 `/biz-gateway` 反代到门户域（示例 `https://dsep-portal-test.minmetals.com.cn`），并透传 `Host`、`X-Real-IP`、`X-Forwarded-For`。
- 业务接口走网关前缀，**不要直连后端域名**；后端服务自身在能力中心登记（如 `app-minmetals-business-base`），前端作为 `fe-minmetals-*` 与后端应用成对登记。

**5）静态资源与共享依赖**
- `/fe-shared-deps` 独立反代到门户域，作为前端共享资源目录。
- 宿主通过 wujie `plugins` 注入共享依赖，让子应用用宿主已加载的依赖，而不是自己再拉一份。

## 3 常见接入问题排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 共享依赖（CommonBundle 等）重复加载，从子应用域名又拉一遍 | 宿主 wujie 没配 `plugins`，子应用用自己的 importmap | 在 `startApp` 增加 `plugins`；Network 面板确认重复请求的来源域名 |
| 共享资源版本不一致、改了不生效 | 协商缓存返回 304 | nginx 对 `/fe-shared-deps` 设置 `etag off; if_modified_since off;` + `Cache-Control: no-store, no-cache, must-revalidate, max-age=0` |
| 子应用内跳转后刷新 404 / 白屏 | SPA 路由没回退 index.html | `try_files $uri $uri/ /micro/<appCode>/index.html` |
| 挂载到门户后样式错乱 | 子应用 base 与部署目录不一致 / 样式未隔离 | 对齐 `publicPath` 与 base；确认隔离方式（shadow DOM 或 scoped） |

## 4 工程命名与业务对应

`fe-` = 前端（node），`app-` = 后端（java maven springboot）：

| 前缀 | 归属 |
|---|---|
| `fm-fis-*` | 财务报账 / 共享报账域（fs 共享运营、ar 应收报账、ap 应付报账、fa 资产报账、rt 关联交易、base 财务报账基础应用） |
| `fm-fia-*` | 应用计算引擎产品线（ara 应收核算、apa 应付核算、base 基础应用） |
| `gu-fin-asset` | 资产核算（独立命名） |

前端工程统一收在 Git `wk-financial-control` 下的 `ace/fe` 组（唯一给出地址的是应收核算前端 `fe-minmetals-fm-fia-ara`）。文档里划分前端负责团队的唯一组织维度是**产品线**：财务 / 应用计算引擎。

> ⚠️ `fia-base` 只以「被调用的**后端**基础服务」出现；`fia-sla` 未检索到同名工程，只有凭证回写相关的 MQ 配置（`sla-voucher-wb-rocketmq`、topic `finance_sla_vou_wb`）。这两个的准确定位请向平台管理员索取 Poseidon 应用清单核对。

## 5 公共组件库的定位（证据有限，别当规范引用）

知识库中**没有 `fe-minmetals-fm-packages` 的任何专门文档**（包名、私服、版本、贡献指南、共享依赖对齐方式全部检索为空）。能确认的只有三条事实：

1. `fe-minmetals-*` 已是平台上前端应用的命名空间，组件库属于其中的**跨业务共享包**，没有独立业务菜单；
2. 集团应用架构蓝图（L2）在「平台公共域 > 技术平台」下明确列有「开发体系、集成体系、运维体系、**通用组件**」，即官方把通用组件定位为**平台横向能力**；
3. L3 详细设计的技术选型表只登记三方库（QianKun、Pinia、Vue Router、Lodash-es、Scss、Vitest、ESLint），**未把公共组件库列为依赖项**；但设计文档里有 `dynamicEditableForm`、`dynamicEditableTable`、`pagination` 等「前端控件」设计章节 —— 说明「可复用控件沉淀成统一组件」在设计层面是既有做法。

**推断（非文档原话）**：它是财务管控平台「通用组件」能力下的跨业务前端共享包，服务 `fe-minmetals-fm-fis-*` 与 `fe-minmetals-business-base` 等多条业务前端，统一基础控件与交互规范，并与微前端宿主形态配合。

要拿到可执行规范，必须索取：组件库 README 与子包清单、npm 私服地址与 `.npmrc`、版本规范（语义化版本/发版权限）、组件贡献指南（分支模型/CR/单测覆盖率/视觉走查）、与微前端共享依赖的注入约定。

## 6 接口规范（现行做法）

知识库里没有一本《统一接口规范》，下面是从《高开代码规范》+ 各 L3/L4 详细设计「错误码规范」章节 + 统一集成平台配置界面拼合出来的现行做法。

### 1）接口分类与鉴权（最硬的规范）

| 接口类型 | 定位 | 鉴权要求 |
|---|---|---|
| `api` | 给前端使用 | **必须在 API 网关统一鉴权** |
| `openapi` | 对外开放能力 | **必须在开放平台网关统一鉴权**；需二次封装保证向下兼容 |
| `innerapi` | 内部系统互调 | 与 client 模块结合 |

内部互调用声明式 HTTP 客户端，返回体统一 `ResVo<T>`：

```java
@HttpExchangeClient(name = "app-cisdigital-base-foundation", path = "/base/foundation/inner-api")
public interface FirstTestClient {
    @GetExchange("/xxx")
    ResVo<String> getXXX(@RequestParam("name") String name);
}
```

两条禁止项：
- **禁用 `context-path`**（防融合部署 URL 冲突）—— 直接影响网关路由/前缀注册；
- 禁止 `RestTemplate`，改用 Spring 6 的 `RestClient` 或 `WebClient`。

### 2）网关 API 注册

入口：统一集成平台 / 门户「能力中心 > 业务网关」。

- **API 条目注册**：所属应用、请求方式、路径（如 `/api/v1/user/login`）、描述、发布状态；分类含平台/应用/系统/业务/数据库/第三方/用户中心/消息中心/文件中心/支付中心。
- **配套治理**：API 分组、API 策略、API 日志、API 统计。
- **参数配置**：`Params / Body / Headers` 三类，登记类型、是否必填、备注、**是否开放**；并提供「查看认证参数」入口 —— 即**鉴权参数由平台统一下发，业务侧不自定义鉴权字段**。
- **状态码与响应明细**：逐个配置每个状态码对应的响应参数明细。
- **异步/调度型接口**单独注册：能力中心 > 调度中心 > 调度接口（编号、名称、所属应用、路径、请求方式、**接口类型同步/异步**、使用状态、返回码）。

### 3）统一响应结构

现行骨架是 **5 个顶层字段 + error 嵌套对象**：

```json
{
  "code": "string",
  "message": "string",
  "data": {},
  "requestId": "string",
  "error": {
    "code": "string",
    "traceId": "string",
    "path": "string",
    "timestamp": 0,
    "details": "string"
  }
}
```

`requestId` 与 `error.traceId` 是链路追踪关键字段，出错时务必回传。

> ⚠️ **存在老口径，需要对齐**：应收报账「分期确认收入报账」接口输出是 `code / message / error / success / data`（`code` 为 String，0 成功）；进项发票红冲返回 `{code:0, message:"", error:"", success:true}`。这两份是旧版四/五字段口径（含 `success`），新接口请以 5 字段骨架为准，跨模块对接时先确认对端口径。

## 7 前端开发的红线

1. **不自建登录、权限、组织体系** —— 全部走平台 SSO 与权限模型。
2. **不自行升级依赖** —— Node 20.x / Vue 3.5.18 / TS 5.x / Vite 6.x，组件严格遵循五矿脚手架 `package.json`。
3. **不手写列表页** —— 用 CurdPage（普通查询 / QueryCard / 高级查询 / 列配置 / 批量操作 / 按行内状态控权限）。
4. **单据状态与审批状态分开映射** —— 两套枚举，别混。
5. **异步结果不假设为同步** —— 付款、票据、凭证编号回传都是异步回写，页面要有「处理中」态。
