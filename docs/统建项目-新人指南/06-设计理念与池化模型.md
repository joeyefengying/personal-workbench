# 06 设计理念与池化模型

> 这一篇解释「为什么长成这样」。看懂后你会发现很多看似绕的设计其实是被业务逼出来的。

## 1 顶层设计理念

| 维度 | 内容 |
|---|---|
| 建设目标 | 落实国资委穿透式监管，构建集团统一的国产化财务管控平台，实现**标准统一、流程协同、数据贯通、管控有效** |
| 总体思路 | 财务管控系统**大集中**，以「财务一体化」支撑「业务一体化」，形成**六大业财闭环** |
| 落地原则 | 集团统建优先（复用标准功能、本地化以配置为主）；业财一体贯通（**业务单据驱动财务凭证**，账实相符）；数据标准统一（物料、客商、科目、组织同源）；安全合规可控（等保 2.0、信创、细粒度权限与审计日志） |
| 架构骨架 | 前台应用（PC/移动）→ 核心报账业务 → 内部协同（资金/总账/共享运营/会计引擎/税务/预算/核算）→ 外部协同（供应链/商旅/项目/成本/合同）→ 基础服务（SSO/权限/用户/组织/工作流/规则引擎） |

### 五个共性业务模式（记这五个词）

1. **单据化** —— 一张业务单据承载全部业务要素，而不是散落在多张表；
2. **池化管理** —— 预付池、应付池、支付申请池、发票池、凭证池、结算池、认领池……；
3. **预算前置校验** —— 提交即校验额度，不是月底算账；
4. **任务化** —— 共享运营用任务池调度，把单据变成「谁的待办」；
5. **主数据统一** —— 组织、客商、科目、物料一套到底。

## 2 各子系统的核心设计理念

### 费用报账
- **理念**：以「费控前置 + 预算校验」控风险，以「事前申请—报销—付款」联动贯通业财；覆盖境内外差旅、通用事前申请、业务招待、一般费用报销、员工借还款、押金保证金退款，配套综合查询与敏感词监控。
- **业务模型**：
  - 事前申请链：以「通用事前申请」为主表（申请ID、组织、申请人、申请总金额），一对多挂「业务明细」「取消通知人」，按业务类型一对一关联具体报销单。
  - 报销链：报销单为主表，一对多关联「关联申请单、发票明细、报销明细、费用分摊、借款核销、收款信息」；**「收款信息」再通过 ID 关联后端「付款申请池」** —— 这就是报账到支付的数据闭环。
- **流程**：经办人发起（填报时预算控制校验）→ 业务审批 → 财务审批 → 进入支付申请池 → 结束。

### 应付报账
- **理念**：以「池化 + 单据族」覆盖采购到付款全链路 —— 应付单据**先进池、再清算**，最终以支付记账单收口。
- **单据族**：付款申请单、退票单、对公费用报销单、预付款单、押金保证金单据、三方抵账等；资金侧预付池/应付池/支付申请池，池内处理与核销后生成**支付记账单**。
- **流程**：发起报账单并业务审批 → 财务审批并汇入应付池 → 判断是否含质保金、退货、扣款、是否立即支付 → 推送支付指令 → 出纳执行 → 支付成功生成支付记账单。

### 应收报账
- **建设目标（五项）**：覆盖「应收单创建—审核—对账—核销—开票」标准化全流程；构建统一应收数据中心（口径规范、实时同步）；核心环节数字化自动化；全周期风险管控（信用额度、账期监控、逾期预警、坏账量化）；多维统计分析。
- **定位**：集团应收业务核心环节与「业务端—财务端」的关键枢纽，为应收核算、资金回收与风险管控提供基础数据。
- **单据族**：暂估收入报账/冲销、通用销售收入报账、通用销售退回、分期确认收入、冶金建设-建造合同收入成本结转，外加收款核销单与发票业务、收入成本结转配置。

### 预算管控
- **理念**：把管控规则与业务单据**解耦** —— 用「预算类别 → 预算模型 → 控制策略 → 控制规则」四层配置表达管控意图，由预算引擎在业务单据提交时执行额度校验（控制执行接口）。
- **模型**：预算组织、预算模型、控制策略、预算调整申请、预算控制事务处理明细、控制匹配规则；引用主数据与外部系统的预算数据。
- **功能域**：预算编制、预算调整、预算模型、预算台账（作为合同/资金计划的管控底座）。

### 资金管理
- **理念**：集中化资金平台 —— 前端对接业务报账，后端对接司库、总账、会计引擎与基础数据中心，形成「报账—结算—核算」闭环。
- **功能域**：资金计划、票据管理、资金池、供应链金融、账户管理、付款管理（结算池、资金结算单、委托付款、司库指令监听）、收款管理（认领池、委托收款）、发布管理（流水发布、票据签收）。
- **配置化模型**：计划类型/模型配置、内外部账户关系、结算方式字典、预警规则（入池超期、疑似重复支付）、黑白名单、内部存款基准利率。

### 共享运营
- **理念**：报账作业集中化 + 任务池调度 —— 以组织/岗位/任务分配规则驱动单据自动分派，支撑共享中心流水线作业。

### 会计引擎（业财翻译官）
- **理念**：**业务数据不变，规则独立配置迭代** —— 财务通过零代码配置成为「规则设计师」，事件模型、来源规则、分录规则、凭证规则是可复用资产。
- **架构**：七块规则库（见 [05 篇](./05-配置与实施注意事项.md)），核心收敛点是「事件分类与单据类型映射」：业务改造升级时只需重定义映射关系，对引擎冲击小。

## 3 为什么设计这么多「池」

池的本质：**把一条跨系统、跨角色、跨时点的长流程，切成若干「状态承接层」**，每层只做一件确定性的事，并对外提供可查询、可批量处理的稳定台账。

文档对三个核心池的定性非常直接：

- **预付池** = 「已支付、但尚未核销的预付款（或保证金）记录的集合或台账」；
- **应付池** = 「已确认入账、待支付的应付账款记录的集合或台账」，且**充当应付报账流程与付款申请之间的桥梁**；
- **支付申请池** = 「已完成业务审批、等待提交或发送给资金模块支付的申请记录的集合」。

它们不是重复设计，而是**三本不同的账**：一本记「钱已付但我还欠着核销动作」，一本记「账已认但我还没付」，一本记「审批完了、等着出纳执行」。池之间靠「源单编号 / 支付申请编码 / 资金结算单编号」串成链路。

### 多池设计解决的四类问题

| 设计动因 | 文档证据 |
|---|---|
| **阶段解耦** | 报账、付款申请、结算、出账分别由业务、财务、出纳推进，需要各自可停留的状态位 |
| **票据统一** | 应付池来源含应付报账单、应付退货单、应付扣款单、质保金转换单；支付申请池来源含收款退回申请单、押金保证金付款/退款 |
| **多轴状态管理** | 支付申请池同时有推送状态（已推送/未推送）与支付状态（未支付/付款成功/付款取消/付款终止）；物理表另有 `approval_status`、`post_status_code`、`pay_status_code` |
| **可追溯与占用核算** | 池记录要反查源单、占用资金计划、记录已认领/未认领金额 |

### 各池速查

| 池 | 作用 | 关键点 |
|---|---|---|
| **预付池** | 已支付未核销的预付款/保证金台账，用于后续核销、冲销 | 入口是预付申请单审批完成；围绕「预付申请单 → 支付指令 → 支付申请基本信息」以及**撤销预付核销申请单**组织 |
| **应付池** | 归集已审批应付账款（合同、项目、订单、供应商、金额、到期日），作为付款申请的数据源 | 流程：报账单审批通过 → 入池 → 池内「发起付款」→ 生成付款申请单。物理表 `payment_ledger`。特殊规则：贸易物资类采购先到票发票报账产生的应付记录**不得发起付款申请**；退货单/扣款单选中应付记录且金额小于剩余金额则更新剩余金额，大于则生成**负数记录行** |
| **支付申请池** | 承接已通过财务审批、等待推送资金模块支付的记录 | 源单联动：财务审核通过 → 源单「已完成」且池中有记录；任一驳回 → 源单回「草稿」且池中**无记录**。物理表 `fin_ap_pay_pool`，关键字段含 `pay_amt`、`remain_amt`、`base_remain_amt`、`currency_code`、`pay_method`、`est_pay_date/pay_date`、`pay_status_code`、`post_status_code`、`approval_status`、`belong_fund_code`、`payable_id_code`、`accounting_entity_code`、`cost_ctr_code`、`src_sys`… |
| **凭证池** | 会计事件 → 凭证（草稿/正式）暂存，传送总账 | 单据生成会计事件即写池；草稿(D)→正式(F)；传送总账后过账，凭证编号**回传**会计引擎 |
| **结算池 / 代付池 / 认领池** | 资金侧收付执行 | 认领池区分「已认领金额 / 未认领金额 / 认领状态」；委托付款与司库指令监听完成对外付款 |

### 三个设计要点，值得抄进自己的模块

1. **池 = 主表 + 占用明细两层**。付款时是「占用」应付记录而不是直接改单据 —— 这才能支持一张应付单分多次付款、多单合并付款。
   > 应付池不是「一张单据一行」，而是「应付记录 + 占用明细」。物理上另有 `fin_ap_pay_pool_plan_dtl`（占用金额、占用日期、占用状态）承接资金计划占用。
2. **双轴状态字段**。审批状态、过账状态、支付状态、推送状态各自独立 —— 一个字段承载不了多套生命周期。
3. **驳回必须同步回滚池**。池记录与源单状态是对偶关系，漏写一侧就会出现「单据驳回了池里还占着额度」的虚占。

## 4 这一篇给你的判断力

以后听到「这个功能放哪个模块」的讨论，先问三句：

1. 它是**业务事实**（→ 报账层）、**状态承接**（→ 池层）、**账务表达**（→ 核算/引擎层），还是**对外收付/报送**（→ 资金/报表层）？
2. 它改变的是单据、池记录，还是凭证？三者生命周期完全不同。
3. 它是同步链路还是「结果回流」异步链路？（资金、票据、付款结果是异步回写的，前端不能只在提交时联动。）
